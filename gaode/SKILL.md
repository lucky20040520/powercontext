# 周边去哪儿：基于高德的地点推荐助手（AMap Surround Explorer）

## 一、用途与适用场景

本 Skill 解决"附近有什么值得去的地方"这一类出行问题。用户用一句话提出需求（城市 + 起点 + 地点类型 + 步行时间上限 + 推荐数量/排序偏好），助手通过高德 MCP Server 查询真实地点、规划步行路线，筛选出符合条件的地点，返回简洁、可信、可核对的推荐。

适用场景：在明确起点附近寻找咖啡馆、餐厅、公园、便利店、书店、健身房、景点等地点，并希望知道步行如何到达、需要多久。评测场景会提供明确的起点坐标，不需要实现设备定位；本 Skill 按单轮"提出需求 → 查询高德 → 返回推荐"完成。长期记忆、多轮反馈、跨城市经验迁移等不是本 Skill 的必做项，单轮完成即可。

## 二、高德 MCP Server 工具（官方）

本 Skill 使用高德官方 MCP Server（@amap/amap-maps-mcp-server）的以下工具：

| 工具 | 能力 | 关键参数 | 返回要点 |
|---|---|---|---|
| `maps_around_search` | 周边搜索：以坐标为中心、按半径搜索 POI（默认按距中心由近及远返回） | `location`（必填，中心点"经度,纬度"）；`keywords`（地点关键词）；`radius`（搜索半径，米） | `pois[]`：`id`、`name`、`address`、`typecode` |
| `maps_text_search` | 关键词搜索：在城市范围内按关键词搜索 POI（兜底补充候选） | `keywords`（必填）；`city`（城市） | `pois[]`：`id`、`name`、`address`、`typecode` |
| `maps_search_detail` | 详情搜索：按 POI ID 获取地点详情 | `id`（必填） | `location`（经度,纬度）、`address`、`business_area`、`city`、`type`、`biz_ext` 等 |
| `maps_direction_walking` | 步行路径规划：规划 100km 以内步行方案 | `origin`（起点"经度,纬度"）；`destination`（终点"经度,纬度"） | `route.paths[]`：`distance`（米）、`duration`（秒）、`steps` |
| `maps_geo` | 地理编码：将地址/地名解析为经纬度（备用） | `address`（必填）；`city` | `location`（经度,纬度） |

关键要点（务必遵守）：

1. **周边搜索/关键词搜索的返回不包含地点坐标**，只含 `id`、`name`、`address`、`typecode`。必须对候选 POI 调用 `maps_search_detail(id)` 获取 `location`（经度,纬度），才能继续规划步行路线。
2. **步行距离与时间一律以 `maps_direction_walking` 的返回为准**（`distance` 单位为米，`duration` 单位为秒）。禁止用直线距离、地图目测或速度估算代替路线查询结果。
3. 若运行环境中工具名略有差异，按能力说明匹配使用（周边搜索/关键词搜索/详情搜索/步行路径规划），调用逻辑不变。

## 三、任务流程（Step-by-Step）

### 第 1 步：理解需求

从用户输入中提取以下要素：

1. **起点坐标**：评测场景会提供明确坐标（格式"经度,纬度"），直接使用。若输入只有地名/地址而没有坐标，先调用 `maps_geo` 解析为坐标；解析失败则如实说明，请用户提供坐标或更明确的位置。
2. **地点类型/关键词**：把自然语言需求转为高德搜索关键词，例如"咖啡馆"→"咖啡/咖啡馆"，"公园"→"公园"，"餐厅"→"餐厅/餐饮"，"书店"→"书店/图书"。若用户描述的是模糊类别（"安静的店""适合自习的地方"），选一个最贴近的可检索类型（如"咖啡"）并说明假设，不要凭空猜类型。
3. **步行时间上限**：如"15 分钟""10 分钟""半小时"。未说明时默认按 15 分钟（900 秒）筛选。
4. **推荐数量**：默认最多 3 个；按用户要求调整（如"2 家"）。
5. **排序偏好**：如"优先近一点的"→ 按步行时间/距离升序；未说明排序偏好时也默认"近的优先"，并在回答中说明排序方式。

若需求本身不完整（如没有地点类型、没有起点），先请用户补充，不要猜测后直接查询。

### 第 2 步：查询候选地点

优先调用 `maps_around_search` 以起点为中心搜索：

- `location` = 起点坐标（"经度,纬度"）；
- `keywords` = 第 1 步确定的地点类型关键词；
- `radius` = 由步行时间上限换算。成年人步行约 80–100 米/分钟，且路线距离通常长于直线距离，**搜索半径取步行可达直线距离的 1.5–2 倍**：

| 步行时间上限 | 估算直线距离 | 建议 radius |
|---|---|---|
| 10 分钟 | 约 800–1000 米 | 1500–2000 米 |
| 15 分钟（默认） | 约 1200–1500 米 | 2000–3000 米 |
| 30 分钟 | 约 2400–3000 米 | 4000–6000 米 |
| 未说明上限 | — | 3000 米 |

候选不足或需要更多选择时：

- 可适当放宽 `radius`（如 5000）再搜一次；
- 或用 `maps_text_search(keywords, city)` 在城市范围内补充候选，再对候选逐个取坐标、算路线，按同样标准筛选。

### 第 3 步：获取候选地点坐标

周边搜索默认按距中心由近及远返回候选，按此顺序处理（建议最多前 10–15 个），逐个调用 `maps_search_detail(id)`：

- 记录该地点的 `location`（经度,纬度）、`name`、`address`、`business_area`、`type`/`typecode` 等字段，作为后续筛选和推荐理由的依据；
- **按 `id` 去重**（同一门店可能出现多条记录）；
- 某候选详情查询失败时，跳过该候选继续处理下一个，不要编造其坐标；
- 用 `typecode`/`type` 与 `name` 核对地点类型是否真正符合用户需求（例如用户要"咖啡馆"，不要把明显不同类型的店列为候选）。

### 第 4 步：规划步行路线

对每个已取得坐标的候选地点，调用 `maps_direction_walking`：

- `origin` = 起点坐标；`destination` = 该候选的 `location`；
- 从返回的 `route.paths` 中取**时间最短**的一条 path，记录其 `distance`（米）与 `duration`（秒）；
- 逐条记录"地点 → 距离 → 时间"的对应关系，回答时必须原样引用这些数据。

### 第 5 步：筛选与排序

1. **严格硬筛选**：只保留 `duration` ≤ 步行时间上限的候选（15 分钟 = 900 秒）。**任何超时的地点都不得列为符合条件推荐**，即使只超几秒；超时候选直接淘汰，不写入推荐表格。
2. **排序**：默认按 `duration`（或 `distance`）升序排列，体现"优先近一点"；若用户明确要求按其他维度（如评分高、更安静等）排序，按其要求排序，并在回答中说明排序依据（评分等非路线数据需有数据来源，否则标"未核实"）。
3. **取前 N 个**（N 默认 3，按用户要求）。不足 N 个时，按实际符合条件的数量推荐，并说明原因（例如"15 分钟步行范围内只找到 1 家符合条件的咖啡馆"）。
4. **回答一致性自检**（提交前必查）：表格中的顺序 = 排序后的顺序；每个地点的距离/时间与第 4 步路线返回完全一致；没有把超时候选写进"符合条件"列表。

### 第 6 步：生成回答

- 用表格或列表呈现推荐，**每项包含：地点名称、地址、预计步行距离与时间、推荐理由**；
- 开头用一句话概括，例如"从起点步行 15 分钟内，为您找到 2 家符合条件的咖啡馆，按距离从近到远排列"；
- 推荐理由必须基于已核实的数据：类型与需求匹配（`typecode`/`type`/名称）、步行时间与距离、地址或商圈、相对起点的位置等；
- 对安静程度、排队情况、营业状态、口味、评分等**没有数据依据的信息，一律标注"未核实"**，不得编造；
- 各推荐地点是从同一起点出发的**独立备选**，不要把它们串成多站行程；
- 语气简洁、直接、可信：给出结论和关键数据即可，不堆砌修饰语。

## 四、回答格式模板

```markdown
从起点出发，步行 15 分钟内为您找到 2 家符合条件的咖啡馆（按距离从近到远）：

| # | 地点 | 地址 | 预计步行 | 推荐理由 |
|---|------|------|----------|----------|
| 1 | 示例咖啡（某店） | 杭州市某路 88 号 | 约 6 分钟 / 480 米 | 距起点最近，步行约 6 分钟，类型为咖啡馆，完全符合需求 |
| 2 | 示例咖啡（另一店） | 杭州市某大厦一层 | 约 12 分钟 / 950 米 | 步行 12 分钟可达，位于某商圈，适合途中停留 |

说明：原计划推荐 3 家，但 15 分钟步行范围内仅检索到 2 家符合条件的咖啡馆；两家店的营业状态与排队情况未核实。
```

- 模板中的地点、距离、时间仅为格式示意，**实际回答必须逐字使用工具返回的真实数据**；
- 时间展示规则：`duration`（秒）换算为分钟时四舍五入到整数分钟并写"约 N 分钟"，例如 372 秒 → 约 6 分钟；不足 60 秒按 1 分钟计。换算要如实，不能夸大或缩小；
- 结果不足、信息未核实或查询失败时，在表格后补充简短说明。

## 五、异常与边界处理

| 情况 | 处理方式 |
|---|---|
| 未找到任何符合条件的候选 | 如实说明"搜索范围内未找到符合条件的 xx"，并建议放宽条件（增大步行时间上限/搜索半径、更换关键词或地点类型），不编造地点 |
| 结果不足指定数量 | 按实际数量推荐，并说明原因（如搜索范围内符合条件的只有 N 家） |
| 工具调用失败 / 高德服务异常 | 如实说明查询失败或服务暂时不可用，建议稍后重试；禁止用编造的地点、坐标、距离、时间作答 |
| 地点类型与需求明显不符 | 不列入推荐，继续检查其他候选 |
| 安静程度、排队、营业状态、口味等无数据依据的信息 | 标注"未核实" |
| 起点无法解析 | 说明情况并请用户提供坐标或更明确的位置描述，再进行查询 |
| 用户需求缺少必要信息（无起点/无地点类型） | 先请用户补充，不猜测 |

## 六、硬性约束（评分关键，不可违反）

1. **数据真实性**：回答中的所有地点名称、地址、坐标、步行距离与时间，必须逐字来自高德工具返回，不得编造或凭常识估计；也不得把候选池外的地点"凑数"进推荐。
2. **步行时间必须来自路线查询**：一律使用 `maps_direction_walking` 返回的 `duration`/`distance`，不得用直线距离或估算替代。
3. **时间限制严格生效**：超时地点不列为符合条件推荐，不因"差一点"破例。
4. **数量限制**：最多推荐 3 个（除非用户明确要求其他数量）。
5. **独立备选**：各推荐地点都是从同一起点出发的独立选项，不要编排成连续多站行程。
6. **密钥安全**：本 Skill 不填写任何 API Key；工具与密钥由运行环境统一配置。
7. **如实说明**：结果不足、信息未核实、查询失败时如实说明，不掩饰、不编造。

## 七、示例（完整流程演示）

用户需求：我在杭州某地铁站附近（起点坐标 120.163209,30.275741，示例占位，以实际输入为准），想找一家咖啡馆，步行不超过 15 分钟，推荐最多 3 家，优先近一点的。

1. **理解需求**：地点类型=咖啡馆；时间上限=15 分钟（900 秒）；数量=3；排序=步行时间升序。
2. **查候选**：`maps_around_search(location="120.163209,30.275741", keywords="咖啡", radius="2500")`，按距中心由近及远得到若干 POI。
3. **取坐标**：按返回顺序对前 10 个候选逐个 `maps_search_detail(id)`，按 `id` 去重，记录各店 `location`、`address`、`typecode`。
4. **算路线**：对每个候选 `maps_direction_walking(origin="120.163209,30.275741", destination=各店location)`，记录时间最短 path 的 `distance`（米）与 `duration`（秒）。
5. **筛选排序**：严格保留 `duration ≤ 900` 秒的候选，按 `duration` 升序取前 3。
6. **自检**：核对表格数据与路线返回一致、无超时候选混入。
7. **回答**：按第四节模板输出表格（名称/地址/预计步行/推荐理由），并附说明。
