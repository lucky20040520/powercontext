# 方案设计：面向软件持续演进的 SDD 上下文管理系统

## 1. 问题定义

在持续维护的软件项目中，四类知识持续演进：

- **需求规格**（做什么）与**接口契约**（怎么做、暴露什么接口）；
- **设计决策**（为什么这么做）；
- **代码实现**（落实规格）；
- **测试验证**（证明实现符合规格）。

AI 开发助手在接任务、改代码、做交接时面临三个问题：

1. **当前任务应遵守什么要求？**——规格与契约会升级，旧版作废；
2. **哪些决策已失效？**——规格演进后，依附旧规格的决策不再成立；
3. **先前验证是否仍适用于当前代码？**——代码变了要重跑，契约变了要重写，
   规格失效了验证作废。

本作品实现一个**工程上下文模块**（SDD Context Manager），用规格版本状态机 +
验证有效性三态判定 + 快照交接，为上述三个问题给出确定性答案。

## 3. 核心设计

### 3.1 规格版本状态机（model.py / registry.py）

- `SpecVersion`：`(id, version, kind, content, status, superseded_by, ...)`，
  `status ∈ {active, superseded, retired}`；
- **登记即演进**：`register_spec(id, v_new)` 自动把同 id 旧 active 版置为
  `superseded`，并记录 `superseded_by`；
- **历史全保留**：`all_versions(id)` 可回看演进轨迹；
- **决策级联失效**：`cascade_invalidate_decisions(spec_id)`——当规格整体失效时，
  依附它的前缀决策全部标记失效（`superseded_by="spec:<id> invalidated"`）。

关键取舍：**不物理删除任何历史**，只改状态。这样交接、审计、回滚都有据可查。

### 3.2 验证有效性三态判定（validity.py）

对每条测试记录（`TestRecord`）按三条规则依次判定：

| 规则 | 判定 | 结果 |
|---|---|---|
| 1. 依据的规格版本仍 active？ | `TestRecord.spec_version` 定位规格 → 状态检查 | 否 → **INVALID** |
| 2. 引用的契约符号仍存在？ | 提取测试 `from X import Y` 符号 + HTTP 端点，与 active 契约声明比对 | 缺符号 → **INVALID** |
| 3. 覆盖代码未变？ | 登记 SHA-256 vs 磁盘当前指纹 | 不一致 → **STALE** |
| 全过 | —— | **VALID** |

设计要点：

- **`spec_version` 是关键字段**：测试登记时记录“依据的规格版本”，
  规格升级后旧测试被正确判为“依据的规格已失效”，而不是误判为 valid；
- **符号提取只取 from-import 与端点**：忽略 `import sys/os` 等标准库、
  类名、方法名，避免断言噪声误伤；
- **指纹缺失保守处理**：无法证明代码未变 → 判 STALE，宁可重跑不可误采信。

### 3.3 任务上下文组装（assembly.py）

- 任务文本 → 关键词（英文标识符整体 + 中文 2/3-gram）→ 与规格标题/正文打分；
- 只取 **active** 规格进入上下文（superseded/retired 绝不出现在“应遵守的要求”中）；
- 相关代码/测试来自规格的 `linked_files / linked_tests`（去重）；
- 相关测试逐个经 ValidityEngine 分级：`valid_tests / stale_tests / invalid_tests`；
- 失效决策按 `related_spec` 与前缀匹配收集，与过期验证一起进 `warnings`；
- `render_prompt()` 输出可直接注入 AI 助手的 Markdown 上下文。

### 3.4 跨会话交接（handoff.py）

- `export_snapshot()` → JSON（schema: `sdd-context-handoff-v1`，含全部规格历史、
  决策、代码快照、测试记录）；
- `import_snapshot()` → 新注册表，状态机完整还原；
- `digest_file()` / `current_hashes()`：磁盘文件指纹；
- `reconcile(paths)`：对账——发现磁盘与登记指纹不一致的文件，返回变更清单
  （**只报变更不改注册表**，由调用方决定是否重登记/重跑测试）。

### 3.5 PowerContext 桥接（可选增强，powercontext_bridge.py）

- `remember(kind=decision|constraint)` 把当前有效规格与失效决策写入
  PowerContext 记忆（Memory），实现跨会话无感召回；
- `search()` 检索既有知识；
- 通过环境变量配置 Server 地址/令牌/Scope；不可用时自动降级，不阻塞主流程。

## 4. 示例工程（demo_project）

为验证“通过实际代码修改验证效果”，构造订单折扣服务示例：

- `specs/requirements_v1.md / contract_v1.md / decision_v1.md` → v2.0 版；
- `src/order_discount.py`：`compute_discount` → 修复负金额（v1.1）→
  `compute_price`（v2.0，重构）；
- `tests/test_order_discount.py`：v1 测试引用旧函数，v2 测试引用新函数。

`scenario_demo.py` 五阶段演示（真实读写代码文件）：

| 阶段 | 动作 | 验证点 |
|---|---|---|
| 0 | 登记 v1 规格/代码/测试/决策 | 状态机建立 |
| 1 | 任务“实现订单折扣” | 上下文只有 v1 active，测试 VALID |
| 2 | 真实写代码修复负金额（v1.1） | 对账发现变更，测试判 STALE |
| 3 | 规格升级到 v2.0 | 上下文只有 v2，DEC-001/002 失效警示 |
| 4 | 真实写代码/测试为 v2，遗留旧测试 | 新测试 VALID，旧测试 INVALID |
| 5 | 交接导出→导入 | 新会话上下文一致、不含失效规格 |

## 5. 非目标与边界

- 不做代码分析（AST/类型推导）：符号提取用正则，够判定契约变化即可；
- 不做自然语言语义匹配：关键词打分够用于演示与工程化初始版本；
- 不修改用户的规格文档：所有登记/演进由 AI 助手或开发者显式调用；
- 与 PowerContext Server 的集成是可选增强，模块主体不依赖外部服务。
