# 方案设计：端侧 AI 推理性能优化与 seekdb 混合检索

> PowerContext 2026 竞赛 · seekdb × 阶跃星辰 赛道 · 端侧 AI 推理性能优化与 seekdb 混合检索
> 基线分支：`2026-competition-ecosystem`；作品目录：`stepfun/`

## 一、作品一句话

一个"浏览器本地向量化 + seekdb 混合检索"的迷你个人知识库：导入语料后在浏览器里用 Transformers.js 本地算 embedding（WebGPU，不支持则自动降级 WASM），向量、原文与元数据写入本地 seekdb（嵌入式），查询时在 seekdb 内完成"向量 + 全文"混合检索并返回排序结果——全程无云端推理 API。

## 二、总体架构

```
┌────────────────────────── 浏览器（用户设备，Chrome/Edge） ──────────────────────────┐
│  Web 应用（Vite 构建）                                                              │
│  ├─ Transformers.js（@huggingface/transformers × onnxruntime-web）                 │
│  │    模型：bge-small-zh-v1.5（中文主模型）/ all-MiniLM-L6-v2（英文副模型）           │
│  │    精度：fp32（基线）/ fp16 / int8 三档可选                                       │
│  │    后端：navigator.gpu 存在 → device='webgpu'（fp16 原生计算），否则 → 'wasm'     │
│  │    界面明确显示当前后端与精度；文档向量化支持批量（batch）并展示进度                  │
│  ├─ 文档导入：粘贴 / 文件上传（.txt/.md），分块（chunk）→ 批量化向量 → 进度           │
│  └─ 检索：查询文本 → 本地查询向量 → POST 到本地服务 → 展示 seekdb 混合检索排序结果     │
└──────────────────────────────────┬──────────────────────────────────────────────────┘
                                   │ REST（127.0.0.1:3000）
┌──────────────────────────────────▼──────────────────────────────────────────────────┐
│  Node 本地服务（stepfun/server/server.js，Express）                                   │
│  ├─ seekdb 嵌入式（@seekdb/js-bindings 原生引擎，库文件在本地 data/ 目录）            │
│  │    database: kb；collection: docs（向量索引 HNSW 512 维 cosine + 全文索引 IK 分词）  │
│  │    embeddingFunction=null：向量一律由浏览器算好后显式传入，服务端不做推理             │
│  ├─ 写入：collection.add(ids, documents, metadatas, embeddings) → refresh_index()     │
│  │    （seekdb 要求写入后刷新索引，刷新后新文档即可被近似向量/混合检索命中）            │
│  ├─ 检索：collection.hybridSearch({query:{whereDocument}, knn:{queryEmbeddings}})     │
│  │    向量与全文两路召回 + RRF 融合全部在 seekdb 内完成，客户端不自行拼合              │
│  └─ 静态服务：前端构建产物 / 本地模型文件 / onnxruntime-web 的 wasm 资产               │
└───────────────────────────────────────────────────────────────────────────────────────┘
```

- **推理位置**：文档向量化、查询向量化全部在浏览器本地执行；模型文件下载/本地加载不改变推理位置，服务端无任何 embedding 计算，无云端 API。
- **存储与检索**：向量、原文、元数据均存于 seekdb；向量检索、全文检索、混合融合均在 seekdb 内完成（`hybridSearch` / `query`），客户端不做两路结果拼合。

## 三、模型与量化方案

| 模型 | 维度 | 语种 | 来源与版本 | 说明 |
|---|---|---|---|---|
| bge-small-zh-v1.5 | 512 | 中文为主 | BAAI/bge-small-zh-v1.5，ONNX 转换版 `Xenova/bge-small-zh-v1.5` | 主模型，中文知识库演示 |
| all-MiniLM-L6-v2 | 384 | 英文 | `Xenova/all-MiniLM-L6-v2`（与 seekdb 官方默认 embedding 同款） | 副模型，英文语料演示 |

量化采用 **INT8（Q8 动态量化）与 FP16（半精度）双方案**，两者均为 embedding 模型端侧部署的标准做法：

- **FP16**：使用官方发布的 `onnx/model_fp16.onnx`（半精度权重）。FP16 是 WebGPU 的原生计算格式，避免 fp32→fp16 运行时转换，且显存/内存占用减半。
- **INT8**：使用官方发布的 `onnx/model_quantized.onnx`（ONNX Runtime 动态量化 Q8，权重 int8，与仓库内 `model_int8.onnx` 同源同量级）。WASM 后端下显著降低内存与计算量。
- **量化处理方式**：`scripts/prepare_models.py` 从 hf-mirror 拉取官方 ONNX 变体并整理为 Transformers.js 可直接加载的目录结构（config.json + tokenizer.json + onnx/model.onnx），并在 `docs/` 记录各文件 SHA-256 与体积，保证可复现。技术说明中附量化前后体积、压缩比与检索质量（Recall@K / nDCG@K）实测对比。

**体积与压缩比（2026-10-28 实测，文件下载后核实）**：

| 模型 | fp32 | fp16 | int8(Q8) | 压缩比 fp16 | 压缩比 int8 |
|---|---|---|---|---|---|
| bge-small-zh-v1.5 | 94,851,877 B (~90.5MB) | 47,497,427 B (~45.3MB) | 24,010,842 B (~22.9MB) | 1.997× | 3.950× |
| all-MiniLM-L6-v2 | 90,387,606 B (~86.2MB) | 45,297,825 B (~43.2MB) | 22,972,370 B (~21.9MB) | 1.996× | 3.935× |

## 四、端侧运行与降级策略

1. **后端选择**：应用启动时检测 `navigator.gpu`（WebGPU 可用性）；可用则显式指定 `device: 'webgpu'`（`@huggingface/transformers` 走 onnxruntime-web WebGPU EP），否则 `device: 'wasm'`（WASM + SIMD/线程）。
2. **自动降级**：WebGPU 初始化/加载失败（GPU 被禁用、驱动问题等）时 try/catch 捕获并自动回退 WASM；界面上方状态栏始终显示当前推理后端（`WebGPU` / `WASM`）与模型精度。
3. **模型加载**：模型文件由本地服务静态提供（`/models/...`），首次加载后 Transformers.js 会缓存到浏览器 Cache Storage，二次加载走缓存（首次/后续分开计时）。
4. **批处理**：文档向量化按 batch（默认 16，可调）分批 `feature-extraction`，进度条实时更新；查询向量化单条即时完成。

## 五、seekdb 存储与混合检索

### 5.1 数据库与集合结构

- **database**：`kb`（嵌入式，数据文件在 `stepfun/server/data/`，随应用启动自动 `CREATE DATABASE IF NOT EXISTS`）。
- **collection**：`docs`，Schema 如下（`server/server.js`）：

```
vectorIndex: VectorIndexConfig({
  hnsw: { dimension: <模型维度 512/384>, distance: "cosine" },
  embeddingFunction: null          // 向量由浏览器计算后显式传入
})
fulltextIndex: FulltextIndexConfig("ik", { ik_mode: "smart" })   // 中文 IK 分词 + 英文
```

- 每条记录：`id`（文档 chunk 的 UUID/序号）、`document`（原文 chunk）、`embedding`（向量）、`metadata`（JSON：文件名、chunk 序号、导入批次、时间戳等）。

### 5.2 混合检索

- 浏览器计算查询向量后调用 `POST /api/search`，服务端执行：
  ```js
  collection.hybridSearch({
    query: { whereDocument: { $contains: <查询关键词> } },   // 全文路
    knn:   { queryEmbeddings: [<查询向量>] },                  // 向量路
    nResults: K,
    include: ["documents", "metadatas"],
  })
  ```
- 关键词由浏览器从查询文本中提取（英文按空白切词取前 N 个、中文整句传入由 IK 分词器切分），全文条件与向量条件同一次调用在 seekdb 内完成召回与 RRF 融合排序，客户端只渲染结果。
- 同时提供纯向量 `query()` 模式（界面可切换"混合 / 向量"两种检索方式）。

### 5.3 增量写入与索引刷新

- 写入：`collection.add()`（支持批量，重复 id 幂等更新），随后调用 `collection.refresh_index()`（底层 `CALL dbms_index_manager.refresh()`，构建/更新 HNSW 与全文索引增量）。
- **已验证**：新增文档 → `refresh_index()` 完成后，向量检索与混合检索立即可命中新文档；刷新前近似向量检索可能查不到（引擎异步建索引），因此应用统一"写入后必刷新"。
- 会话/集合状态：前端用 localStorage 记录当前会话（模型、精度、集合名、文档数、后端类型）；服务端按 database+collection 幂等建库建集合，支持"清空知识库"（删集合重建）与连续导入。

## 六、性能优化与评测方法

### 6.1 优化点

| 环节 | 优化手段 |
|---|---|
| 模型加载 | 本地模型文件 + 浏览器缓存复用；加载后 warm-up 一次推理再计时 |
| 文档向量化 | 批量 feature-extraction（batch=16 默认），WebGPU 下并行张量计算 |
| 写入 | seekdb `add` 批量提交（一批 100 chunk），减少往返 |
| 索引刷新 | 增量导入统一批量后再 `refresh_index()` 一次（避免每批刷新的固定开销） |
| 查询 | 查询向量单次推理；`hybridSearch` 单 SQL 内完成融合，避免客户端拼合 |
| 后端选择 | 优先 WebGPU（fp16 原生），减少 WASM 下 fp32 内存拷贝 |

### 6.2 评测方法（应用内置"评测"面板，结果来自真实浏览器运行）

- **检索质量**：内置评测集（中文 72 篇语料 + 20 条查询、英文 24 篇 + 10 条查询，每条查询标注 1~2 个相关文档 id），分别用 fp32/fp16/int8 跑 `hybridSearch`，计算 Recall@5 与 nDCG@5，报告与 fp32 基线的差值。
- **性能**：分阶段计时——模型下载/加载、文档向量化（吞吐 doc/s）、写入、索引刷新、查询向量化、seekdb 检索、端到端（提交查询→结果展示）；区分首次（冷加载）与预热后（热查询）；每个配置重复 ≥3 次取中位数；分别报告 WebGPU 与 WASM 两条路径。
- **降级验证**：正常环境验证 WebGPU；通过界面"强制 WASM"开关模拟不支持环境，验证提示与 WASM 下完整检索流程。
